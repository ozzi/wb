# Проверка шаблонов Modbus TCP без устройства

Шаблоны `templates/config-*.json` — это не код, а описание регистров для драйвера
`wb-mqtt-serial`. Их не ловит ни один тест wb-rules, а ошибки в них видны только
на живом обмене. Поэтому две проверки: статическая и по обмену.

## Статическая проверка

```bash
node tests/modbus-template-check.js templates/*.json   # можно несколько файлов
node tests/modbus-template-check.test.js               # проверка самой проверки
```

Обе команды и прогон по всем `templates/config-*.json` выполняет CI
(`.github/workflows/tests.yml`), поэтому регрессия в шаблоне видна в PR, а не на железе.

Скрипт ищет то, что драйвер проглотит молча, а потом отдаст мусор в MQTT:

- дубль `id` канала — два канала с одним именем в MQTT-дереве конфликтуют;
- неизвестный `format` (драйвер молча читает его как `u16`) и `error_value`, который не
  помещается в разрядность формата;
- `word_order`: допустимы только `big_endian` и `little_endian` (`WordOrderFromName` в
  `src/register.h`); всё остальное, включая `little` и `le`, молча читается как
  big-endian. Проверка требует `word_order` у любого регистра шире 16 бит и отвергает
  его у 16-битных как бесполезный;
- неизвестный `reg_type`: драйвер знает `holding`, `holding_single`, `holding_multi`,
  `input`, `coil`, `discrete`, `press_counter` (`src/modbus_device.cpp`);
- перекрытие адресов друг другом и выход за 0..65535;
- `max_read_registers` и `max_reg_hole` разбираются как в драйвере: `0` и значения больше
  125 приводятся к 125, а если параметр не задан вовсе — действует умолчание 1 (README
  драйвера, раздел про параметры устройства);
- группировку регистров в запросы по правилам `AddRegister` из `src/modbus_common.cpp`
  (внутри одного адресного пространства: `holding`, `input`, `coil` и `discrete` —
  разные пространства, между ними драйвер запросы не склеивает):
  регистр попадает в текущий диапазон, если отделён дырой не больше `max_reg_hole` и
  диапазон после этого не длиннее `max_read_registers`. Печатается карта групп с полным
  составом каналов; канал, не попавший ни в одну группу, — ошибка.

Порядок обхода регистров скрипт берёт по возрастанию адреса, как требует `AddRegister`
(регистр ниже начала диапазона не добавляется). Порядок самих запросов к устройству
зависит от планировщика (`poll_plan.h`) и в карте не отражён — карта отвечает на вопрос
«какие каналы читаются вместе», а не «в каком порядке придут запросы».

`max_reg_hole` скрипт не ограничивает: драйвер его не ограничивает тоже. Значение 10 из
`MAX_HOLE_CONTINUOUS_16_BIT_REGISTERS` — это минимум, который драйвер сам поднимает для
WB-устройств с включённым continuous read, а не предел для обычных Modbus-устройств.

Проверять надо все шаблоны, а не только новый: скрипт принимает путь файла.

## Проверка по обмену (эмулятор)

Адреса эмулятор не проверяет, он проверяет транспорт, масштабы и порядок слов. Годится,
когда устройство временно недоступно: поднять Modbus TCP-сервер и завести его адрес как
`modbus tcp` с тем же шаблоном.

```python
from pymodbus.datastore import (ModbusSequentialDataBlock, ModbusServerContext,
                                ModbusSlaveContext)
from pymodbus.server import StartTcpServer

ctx = ModbusServerContext(slaves=ModbusSlaveContext(
    hr=ModbusSequentialDataBlock(0, [0] * 400)), single=True)
StartTcpServer(context=ctx, address=("0.0.0.0", 1502))
```

Эмулятор отдаёт нули, поэтому: каналы должны появиться со значением `0` и без
`meta/error` — так ловится `error_value`, совпавший с нормальным значением, и развал
группы запросов. Масштаб на нулях не проверить; для этого в эмуляторе нужно прописать
осмысленные значения в нужные регистры.

Порядок работы: адреса — по документации производителя, транспорт и арифметика —
по эмулятору, смысл значений — по живому устройству. Перепутанный адрес эмулятор
покажет как ноль и «всё зелёное».
